# R3-5 C0 customer acceptance and receipt contract

Status: **ENTRY CONTRACT PREPARED / IMPLEMENTATION DEPENDENCY-BLOCKED**

R3-5 begins only after R3-4 immutable proposal versions are independently
accepted. This contract defines a narrow proposal-review and acceptance room;
it does not create the later full customer portal.

## 1. Smallest truthful outcome

A customer possessing a purpose-bound, expiring action link can view one exact
immutable proposal version, ask a question, request changes, decline, or choose
`Accept proposal`. Acceptance requires a signer-entered name, approved consent
wording, the exact proposal-version hashes and an immutable timestamp. Veltex
returns a durable receipt to the customer and notifies the owning organization.

The product uses `Accept proposal`, `accepted proposal` and `acceptance
receipt`. It must not claim an electronic signature, signed contract, legal
advice or guaranteed enforceability unless later counsel approval explicitly
authorizes that language and workflow.

## 2. Security boundary

1. Issue CSPRNG tokens with at least 128 bits of entropy. Store only a keyed
   hash; never store or log the bearer token.
2. Bind each token to organization, proposal version, purpose, expiry and
   revocation state. Acceptance requires the `accept_proposal` purpose; a
   view-only or legacy tracking token cannot accept.
3. Resolve the token through one security-definer boundary with a fixed search
   path, explicit grants and uniform invalid/expired/revoked responses.
4. Rate-limit resolution and mutation by token hash and privacy-bounded network
   signal. Do not leak organization, customer or version existence.
5. Rotate/revoke links without modifying the immutable proposal version or an
   existing receipt. Forwarded-link risk is stated clearly; the operator may
   require a designated approver email match as an organization policy.
6. Existing plaintext tracking identifiers and mutable `proposals.status`
   cannot be promoted into acceptance authority or receipt evidence.

## 3. Additive records

### `crm_customer_action_tokens`

- organization and immutable proposal-version IDs;
- keyed token hash and key version;
- purpose (`review`, `respond`, `accept`);
- optional normalized designated-approver email hash;
- issued, expires, revoked and last-resolved timestamps;
- created/revoked actor IDs and reason; and
- unique active token identity and organization-bound foreign keys.

Raw token bytes never persist. Authenticated users receive issuance metadata,
not the existing bearer value.

### `crm_proposal_responses`

Append-only customer responses scoped to the exact proposal version:

- response kind (`question`, `change_requested`, `declined`);
- bounded customer-entered message;
- optional signer-entered display identity;
- token ID, request key, content hash, created timestamp; and
- organization/proposal-version binding.

Decline and change requests do not alter immutable proposal bytes. The operator
must publish a new R3-4 version for revised terms.

### `crm_proposal_acceptance_receipts`

One immutable accepted receipt per proposal version:

- organization, proposal version, opportunity and selected package IDs;
- signer-entered full name and normalized email;
- optional designated-approver-match result;
- consent text and consent-version identifier;
- proposal content/rendered hashes copied from the accepted version;
- acceptance timestamp generated by PostgreSQL;
- token ID, request key and canonical receipt hash; and
- privacy-bounded source metadata sufficient for abuse investigation without
  storing sensitive browser fingerprints.

No UPDATE or DELETE path ships. Correction requires revoking the commercial
effect through a later reason-coded workflow; it never rewrites history.

## 4. Acceptance command

`command_crm_accept_proposal_version(token, request_key, signer_name,
signer_email, consent_version, accepted_package_ids)` must:

1. validate token hash, key version, purpose, expiry and revocation before
   returning any object detail;
2. lock the token, proposal version, opportunity and selected packages;
3. require exact stored proposal-version hashes and approved consent version;
4. require every selected package to belong to the same organization,
   opportunity, property and proposal version;
5. reject empty or unreasonably long identity fields and normalize email
   without presenting it as identity verification;
6. create one canonical receipt and return it on an exact retry;
7. reject changed reuse, a second conflicting acceptance, stale versions and
   acceptance of superseded/revoked proposal versions;
8. move only the accepted packages to `accepted`; leave declined/unselected
   packages unchanged;
9. mark the parent opportunity `won` through the existing stage command only
   when at least one package is accepted, setting acceptance method to the C0
   receipt—not the legacy/manual path;
10. emit identifier-only audit/outbox events for acceptance and the required
    operator notification; and
11. revoke remaining accept-purpose tokens for that exact version after the
    receipt commits.

The database owns atomic state movement. A browser route must not separately
write receipt, package and opportunity state.

## 5. Customer-safe projection

The token resolver returns only:

- organization customer-facing display identity;
- immutable proposal-version customer-visible snapshot and rendered content;
- version number, price, currency and pricing basis;
- expiry and allowed actions;
- approved consent wording; and
- receipt-safe result after acceptance.

It excludes costs, wages, margins, overhead, access notes, internal scope
notes, raw walkthrough evidence, estimator identity, provider IDs, audit rows,
other customers/properties and all other proposal versions.

## 6. Operator and customer experience

- Review, question, change request, decline and accept are visibly distinct.
- Acceptance requires an unchecked confirmation control, signer name and
  email; no preselected consent.
- The confirmation screen repeats the exact version number, amount, scope and
  consent text before commit.
- A successful result shows a stable receipt identifier, accepted timestamp,
  signer-entered identity, proposal-version hash summary and downloadable or
  printable receipt view.
- Refresh and exact resubmission return the same receipt. Network interruption
  cannot create duplicates or leave package/opportunity state partially moved.
- Errors preserve entered non-secret fields and use uniform, non-enumerating
  messaging for invalid/expired/revoked links.
- Desktop and genuine 390px acceptance require keyboard operation, focus
  management, live messages, 44px targets, no horizontal overflow and WCAG
  2.2 AA target evidence for the bounded room.

## 7. Required operator notification

R3-5 records an `acceptance_received` outbox event with identifiers only. R3-8
owns delivery policy, retry, suppression and operator channel configuration.
Until R3-8 is accepted, CRM must still surface the new acceptance in-app; R3-5
must not claim an email or SMS was sent.

## 8. Explicit exclusions

- electronic-signature or legal-enforceability claims;
- identity-document, biometric or knowledge-based verification;
- payment, deposit collection, invoicing or subscription billing;
- full portal accounts, document libraries or customer administration;
- proposal editing by the customer;
- handoff, scheduling or field-service creation; and
- marketing messages or consent inferred from proposal acceptance.

## 9. Required proof

### Security and database

- fresh migration replay and definer/grant allowlist;
- raw-token absence across database, logs, errors, audit and outbox;
- token entropy, hash/key rotation, expiry, revocation, purpose and legacy-link
  refusal tests;
- cross-tenant, cross-version, cross-package, forwarding/designated-approver
  and IDOR negatives;
- exact retry, changed retry, concurrent double-submit and partial-failure
  atomicity proof;
- immutable version/hash/consent binding and direct-DML denial; and
- multi-package acceptance with correct parent/package outcomes.

### Product and truthfulness

- question/change/decline/accept paths on desktop and genuine 390px;
- expired, revoked and already-accepted recovery;
- receipt persistence across refresh and exact content/hash correspondence;
- accessibility scan plus keyboard/screen-reader operator checks; and
- copy audit proving no signature, contract-guarantee, payment or delivery
  claim beyond available evidence.

### Release gates

- counsel-approved acceptance/consent wording or an explicit founder decision
  to retain the non-signature C0 wording pending counsel;
- focused/full tests, TypeScript, build, migration and disposable-database
  harness;
- exact independent Claude `PASS`, complementary accessibility/customer-flow
  review, guarded Preview execution and synthetic acceptance proof;
- real operator/customer-format validation without real customer acceptance in
  Preview; and
- explicit founder acceptance limited to R3-5.

## 10. Next action

Do not implement R3-5 until R3-4 is independently accepted. Preserve this
contract as the technical and truthfulness boundary; resolve final consent copy
before enabling any public acceptance action.
